# 现有界面判断

当前 GUI 已具备基本可用能力：

1.  任务管理页可以配置任务、批量导入、自动生成书名、设置输出格式、图片质量、排序和分卷，并启动任务。
2.  登录页可以通过知乎 webview 完成登录。
3.  运行日志页可以查看 `runtime.log`，支持自动刷新、手动刷新、清空日志和打开输出目录。
4.  数据浏览页可以查看数据库中的文章、回答、想法等汇总数量。
5.  调试面板和开发者工具入口已经存在，方便开发排查问题。

主要问题是：界面仍偏向开发者和高级用户，主流程没有被突出；普通用户需要理解任务类型、生成模式、排序规则、跳过抓取、日志内容等概念，才能判断下一步该做什么。

# 待改进项

## P0：优先完成，保证小白用户能走通主流程

1.  增加新手默认流程
    1.  将首页调整为流程式工作台，突出“登录 -> 粘贴链接 -> 开始生成 -> 打开结果”。
    2.  默认不要求用户理解任务类型、排序、生成模式等高级概念。
2.  增加登录状态卡片
    1.  在首页或顶部明确展示“已登录 / 未登录 / 登录失效”。
    2.  未登录时启动任务前直接引导到登录页。
    3.  登录成功后提供重新检测和退出登录动作。
3.  简化任务输入
    1.  默认提供一个“粘贴知乎链接”的输入区，支持单条和多条链接。
    2.  自动解析任务类型和任务 id，并展示识别结果。
    3.  无效链接要展示具体原因，不能只显示“未解析到任务id”。
4.  分离默认模式和高级模式
    1.  默认模式只保留书名、输出格式、图片质量等常用配置。
    2.  排序、生成模式、跳过抓取、分卷、备注等配置放入高级模式。
5.  增加启动前检查
    1.  检查登录状态、任务有效性、输出格式、输出目录权限和配置保存结果。
    2.  检查失败时阻止启动，并给出明确的修复动作。
6.  优化运行状态展示
    1.  将原始日志升级为阶段化状态：初始化、抓取、入库、生成 HTML、生成 EPUB、完成。
    2.  普通用户默认看阶段和错误摘要，原始日志放到折叠区域。
7.  增加完成页和结果入口
    1.  任务完成后直接展示生成结果。
    2.  提供打开输出目录、打开 HTML、复制输出路径、重新生成等动作。
8.  隐藏调试入口
    1.  调试面板、开发者工具、js-rpc 开发者工具默认不出现在普通用户主流程中。
    2.  需要时通过开发者模式启用。

# 任务边界拆分

## 前端任务目标

前端负责用户可见的主流程和交互体验，目标是把当前专家表单改造成普通用户能直接跟随的工作台。

1.  新手默认流程
    1.  首页默认展示“登录 -> 粘贴链接 -> 开始生成 -> 打开结果”的任务路径。
    2.  将调试页、复杂排序、跳过抓取、分卷、备注等低频能力后置到高级模式。
2.  任务输入与预览
    1.  支持单条和多条知乎链接输入。
    2.  前端即时解析任务类型和任务 id，并展示识别结果。
    3.  对无效链接展示错误原因和修复建议。
3.  输出配置
    1.  默认模式只保留书名、输出格式、图片质量。
    2.  高级模式保留生成模式、排序规则、跳过抓取、自动分卷等完整能力。
4.  运行状态与完成页
    1.  将结构化日志转成阶段状态：初始化、抓取、入库、生成、输出、完成。
    2.  任务完成后展示输出结果入口，而不是只依赖系统自动打开文件夹。
5.  调试能力隔离
    1.  普通用户主导航默认不展示调试面板。
    2.  开发者模式开启后再展示调试面板和开发者工具入口。

## Electron 任务目标

Electron 负责 GUI 与本地能力、会话、文件系统和后端 workflow 的连接，目标是给前端提供稳定、可解释的 IPC 能力。

1.  登录态检测
    1.  复用 `zhihu-http-get` 或封装明确的登录检测能力。
    2.  将“已登录 / 未登录 / 登录失效 / 检测失败”返回给前端用于状态展示。
2.  任务运行锁
    1.  保留当前 `isRunning` 防重入能力。
    2.  任务运行中向前端返回明确状态，避免重复启动。
3.  IPC 返回结构
    1.  优先复用现有 IPC：`start-customer-task`、`zhihu-http-get`、`get-log-content`、`get-runtime-jsonl-content`、`get-db-summary-info`、`open-output-dir`、`clear-all-session-storage`。
    2.  后续如需新增 IPC，只围绕任务运行状态、输出结果、诊断信息三类能力设计。
4.  输出目录与结果入口
    1.  继续提供打开输出目录能力。
    2.  后续可补充最近一次输出路径、HTML 入口和 EPUB 路径，供完成页展示。
5.  调试能力隔离
    1.  `open-devtools` 和 `open-js-rpc-window-devtools` 保留给开发者模式。
    2.  普通用户界面不直接暴露这些入口。

## 后端任务目标

后端负责实际任务执行、结构化日志和输出结果记录，目标是让前端不必解析难读的纯文本日志。

1.  结构化日志阶段补齐
    1.  基于现有 `runtime.jsonl` 和 `Logger.event`，补齐 init、fetch、persist、generate、render、output 等关键阶段。
    2.  每个阶段至少记录开始、成功、失败状态。
2.  任务执行状态
    1.  在 workflow 中持续记录当前任务 runId、阶段、状态、耗时和错误。
    2.  为前端状态面板提供稳定数据来源。
3.  输出结果记录
    1.  任务完成后记录输出目录、HTML 输出、EPUB 输出、书名和输出格式。
    2.  支持前端完成页和后续输出历史读取。
4.  错误摘要
    1.  失败时记录用户可读的错误摘要和原始异常信息。
    2.  前端默认展示摘要，详细异常放入诊断区。
5.  诊断包数据来源
    1.  后续诊断包应包含最近配置、运行日志、结构化日志、数据库摘要和环境信息。
    2.  本轮只规划目标，不新增诊断包接口。

# 开发规划

## M1：默认闭环

1.  前端实现流程式首页、登录状态卡片、简化任务输入和默认输出配置。
2.  Electron 提供稳定的登录态检查、任务启动返回和运行中防重复启动提示。
3.  后端保证任务开始、完成、失败能写入结构化日志。
4.  验收目标：新安装用户不看 README，也能完成一次“登录 -> 粘贴链接 -> 生成 -> 打开结果”。

## M2：运行状态

1.  前端实现阶段化运行状态面板和原始日志折叠区。
2.  Electron 稳定读取 `runtime.jsonl`，并兼容 `runtime.log`。
3.  后端补齐 init、fetch、generate、output 等阶段事件。
4.  验收目标：用户不用读原始日志，也能判断任务运行阶段、成功或失败原因。

## M3：高级能力与调试分层

1.  前端拆分默认模式和高级模式。
2.  Electron 将开发者工具入口限制在开发者模式中。
3.  后端无需为普通用户流程暴露调试概念，但继续保留结构化诊断信息。
4.  验收目标：普通用户主界面不出现调试面板，高级用户仍能找到完整配置能力。

## M4：历史与诊断

1.  前端增加最近任务、输出历史、诊断导出入口和增强数据浏览。
2.  Electron 负责读取输出路径、日志和诊断数据。
3.  后端记录输出结果和更完整的错误摘要。
4.  验收目标：用户可以打开历史产物，并能一键准备反馈 bug 所需信息。

# 与后端的协作点

1.  运行状态面板最好使用结构化日志或阶段事件。当前项目已有 `runtime.jsonl`，可以优先基于它做解析。
2.  任务预览如果要展示默认标题，可以复用或扩展 `get-task-default-title`。
3.  输出历史需要记录任务开始时间、完成时间、输出路径和输出格式，可以先在前端本地持久化。
4.  暂停任务、取消任务不建议作为当前 P0 目标，除非后端工作流先提供可中断能力。
