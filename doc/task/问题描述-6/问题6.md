# 问题6：补全日志、链路文档与自动化测试

## 结论

需求信息已经齐全，可以进入全量开发。本文件中的选择均为最终约定，不再保留已完成的确认问答。

目标是在不改变页面与既有业务逻辑的前提下：

1. 梳理前后端主要链路，在 `doc/开发文档` 中补全 Mermaid 流程图。
2. 建立前后端一致的结构化 JSONL 运行日志，使“日志 + 问题描述”可以直接关联到故障模块和源码入口。
3. 建立离线可重复、业务数据隔离的自动化测试，并提供显式的知乎在线冒烟与 fixture 更新能力。
4. 继续使用当前最新兼容依赖，不通过降级依赖解决兼容问题。

## 二、日志契约

### 2.1 统一字段与常量

前后端复用同一份纯 TypeScript 日志契约，至少包含：

```text
schemaVersion / triggerAt / traceId / runId / jobId / eventCode /
source / stage / status / level / message / durationMs /
taskType / entityType / entityId / details / error
```

- `eventCode`、`stage`、`status`、`level`、schema 版本及脱敏键必须使用共享常量，禁止魔法字符串。
- 实际执行的关键阶段记录一次 `start`，随后恰好记录一个终态：`success`、`failure` 或 `partial_success`。
- `progress` 是非终态；未执行的可选阶段可使用独立 `skip` 事件，但不能在已经 `start` 后用 `skip` 代替终态。
- `traceId` 从 IPC/命令入口贯穿调用链；`runId` 标识一次 Workflow；`jobId` 标识可独立追踪的子任务。
- 开发文档维护“事件编号 → 模块/源码入口 → 常见原因 → 排查建议”的诊断表。

### 2.2 文件与保留策略

所有运行日志默认写入 `PathConfig.rootPath/log`：

- 后端文本日志：`runtime.YYYY-MM-DD.log`
- 后端结构化日志：`runtime.YYYY-MM-DD.jsonl`
- 前端结构化日志：`frontend.runtime.YYYY-MM-DD.jsonl`

日期使用本地自然日。每类日志分别只保留最近 5 个日期文件，超过后自动删除更早的文件；单个日期文件不限制大小。测试可通过运行上下文把日志目录改到临时目录，这是默认路径的唯一测试例外。

生产环境记录错误、关键用户操作、关键 Workflow 和 IPC；调试模式额外记录 info/debug。日志写入失败必须安全降级到控制台或内存诊断，不能掩盖原始业务异常或导致应用崩溃。

GUI 输出历史从最近 5 日的后端 JSONL 中读取，只接受 `success` 或 `partial_success` 的显式 `output.created`，按输出标识去重并倒序展示，保留局部成功告警状态，并忽略可诊断的损坏行。第 6 日清理旧日志时，对应的旧输出历史同步消失，不建立独立永久索引。

### 2.3 前端日志 IPC

- 前端通过专用的被动 IPC 批量写入日志，避免“记录日志的 IPC 再触发日志记录”形成递归。
- 默认每 500ms 或累计 20 条刷新一次，错误事件立即刷新；单条序列化后最大 64 KiB。
- 主进程必须校验 schema、批量大小与单条大小，非法 payload 返回明确错误且不写盘。
- 前端覆盖应用启动、页面切换、关键操作、IPC 开始/成功/失败、React Error Boundary、全局 `error` 与 `unhandledrejection`；不记录普通输入过程和高频渲染状态。
- 普通业务调用由 renderer 附加 `traceId`；使用统一日志包装的 IPC 在主进程派生 `jobId`，启动任务时再创建 `runId` 并贯穿 workflow。日志轮询、输出历史轮询和前端日志接收走防递归的被动通道，不伪造通用起止事件。
- 任务配置、默认标题、数据库分页/导出和本地输出路径等带 payload 的关键入口在副作用前校验对象形状与字段范围；非法输入记录唯一 failure 并拒绝执行。

### 2.4 脱敏

前端、后端、测试输出和 fixture 统一递归脱敏：

- 禁止写入 Cookie、Authorization、完整请求头、完整知乎响应正文和用户输入的长文本。
- 敏感键不区分大小写；嵌套对象、数组和非 Error 异常同样处理。
- URL 查询参数、文件路径、用户/内容 ID 只保留定位所需摘要。
- 日志序列化失败时输出安全摘要，不回退为原始对象全文。

## 三、错误传播与行为边界

- 网络、签名、认证、配置及无法继续的持久化错误必须向上抛出，并使对应命令或 Workflow 失败。
- 批量任务中可恢复的实体级失败汇总为 `partial_success`，记录成功数、失败数和脱敏后的失败实体，不得伪装为 success。
- 同一 trace 不能先记录 failure 又记录 success。
- 登录检查必须区分有效 Cookie、失效 Cookie、正常空数据、权限限制和网络失败，不能以“返回了空数组或 data 字段”作为成功。
- 允许修复新增测试暴露的真实逻辑缺陷，包括异常吞噬、任务超时计时器清理和分卷边界计数；不做无关重构。
- 已有旧配置 schema 继续被明确拒绝并给出可理解的诊断，本期不新增旧配置迁移。
- `PathConfig.rootPath` 在部分安装目录可能不可写，这是已接受边界；必须通过安全降级保证主流程仍可运行。
- 知乎分页响应只有显式 `data` 数组才是有效列表；合法空数组与缺失/损坏响应必须区分。所有分页数量必须是非负整数；收藏夹优先校验 `item_count`，仅在它缺失时兼容校验 `answer_count` 并告警，校验通过后才能持久化元信息。
- 配置加载失败时保留安全默认 UI 但禁止启动，避免覆盖旧/损坏配置；数据库摘要或列表 IPC 失败必须展示独立失败态，不能冒充空数据。
- 输出文件名必须清理 Windows 非法字符和路径穿越、限制长度并以稳定摘要区分超长分卷；Windows + Node.js 24 的中文目录复制不用 `fs.cpSync`。EPUB 的 `mimetype` 作为首个 STORE 条目，OPF/TOC 正确 XML 转义并按图片扩展名写 MIME。

## 四、测试分层与命令

使用 Vitest workspace。根目录提供以下命令：

| 命令 | 是否联网 | 内容 |
| --- | --- | --- |
| `pnpm test` | 否 | 后端单元、前端组件、本地集成测试，并生成覆盖率报告 |
| `pnpm test:unit` | 否 | 纯逻辑与后端单元测试 |
| `pnpm test:client` | 否 | jsdom 前端组件与 IPC mock 测试 |
| `pnpm test:integration` | 否 | 临时目录、SQLite 与固定 fixture 的集成测试 |
| `pnpm test:online` | 是 | 启动可见 Electron 签名运行时并执行低请求量在线冒烟 |
| `pnpm fixtures:refresh` | 是 | 显式采集、脱敏和更新 fixture，输出待人工审阅 diff |

`pnpm test` 永不联网，也不得读取仓库根配置。只有 `pnpm test:online` 与 `pnpm fixtures:refresh` 可以只读仓库根 `config.json.request.cookie`。Cookie 不存在、为空、格式错误或失效时，在线命令必须明确失败并返回非零，且不得打印 Cookie。

在线命令允许显示 Electron 窗口，但只把 Electron 用作签名运行时，不进行真实 UI E2E 操作。签名运行时与在线测试本身也必须产生日志。

### 4.2 前端组件测试

覆盖首页 Hook 顺序、任务表单、登录状态、运行阶段、输出历史、数据浏览、调试面板、前端日志与日志 IPC。IPC 使用 mock；必须覆盖 loading、成功、失败、空数据、非法 payload 及日志 IPC 不递归。

### 4.3 本地集成测试

覆盖 init → fetch → persist → generate 完整 Workflow、各类 fixture 解析、分页与子任务扩展、SQLite 关系、HTML/EPUB 输出、前后端日志汇聚、IPC 契约和测试现场清理。

所有离线测试使用独立临时目录，配置、SQLite、缓存、日志和输出均不得指向现有业务数据。涉及全局 PathConfig、HTTP cache、任务池和 Knex 的测试默认串行或进程隔离；结束时销毁数据库连接、清除计时器并恢复全局状态。初始化中的版本联网检查必须可注入并在离线测试中禁用。

默认清理测试产物；设置 `KEEP_TEST_ARTIFACTS=1` 时保留并打印目录位置。

### 4.4 在线冒烟与 fixture

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| O01 | config.json 不存在或 Cookie 为空 | 明确失败并返回非零 |
| O02 | Cookie 格式错误或失效 | 明确失败，不把空数据当成功，不泄露 Cookie |
| O03 | 有效 Cookie 与最小签名请求 | 返回稳定字段并记录脱敏诊断和耗时 |
| O04 | 单条回答、文章、想法 | 分别读取并通过 fixture schema 校验 |
| O05 | 问题、话题、收藏夹、专栏 | 各读取 1–2 页并验证分页结束和混合关系 |
| O06 | 用户型任务 | 覆盖公开列表首个有效页及分页结束 |
| O07 | 空列表、删除或 404 | 在线场景可选；离线 fixture 必须区分各类错误 |
| O08 | fixture 更新 | 脱敏、裁剪、校验、离线回归通过并生成人工审阅摘要 |

在线测试不能只断言“没有抛错”，必须检查稳定实体字段，并在涉及抓取链路时检查临时 SQLite 中的预期记录。

fixture 只能由 `pnpm fixtures:refresh` 显式更新。每份 fixture 包含 schemaVersion、sourceType、sourceUrl、capturedAt 和内容校验值，仅保存测试需要的最小字段；更新时先在临时 staging 目录完成采集，再核对文件集合，以及 manifest 的名称、类型、URL、稳定实体 id、分页 offset/条数和收藏夹去重语义，随后运行离线回归并人工检查 diff。`pnpm test:online` 只按类型选择代表样本，不改写 fixture；`online: false` 的空/404 候选只保留离线覆盖。

## 六、验收标准

1. 七张流程图及任务类型差异表完整，技术栈与当前代码一致。
2. 关键执行阶段满足“一个 start + 一个终态”，日志可通过关联 ID 和事件编号定位源码。
3. 前后端日志按日写入、脱敏并各保留最近 5 日；输出历史与该窗口一致。
4. 离线三层测试通过并生成覆盖率报告，不联网、不读取或污染业务数据。
5. 在线测试与 fixture 首次采集通过；Cookie 失败路径返回非零且不泄露敏感信息。
6. 类型检查、前后端构建通过。
7. `pnpm start` 仍只启动已有 `dist/index.js`；开发时由 `pnpm watch` 单独构建，前端通过 `pnpm startgui` 配合 Electron 调试。
8. 不设置全仓覆盖率硬阈值，但报告必须可供后续补测使用。
