# 问题 9：支持导出 Markdown 格式并迁移后端 ESM

## 当前状态

全量开发与本地验收已经完成。HTML 转 Markdown、后端原生 ESM 迁移、三格式强制输出、多文件转换、最近五日历史、GPL 发行材料和对应源码发布流程均已落地，当前没有遗留确认项或阻断缺陷。

## 原始需求

目前已经支持 HTML 格式输出，但用于 AI 分析时，移除布局和样式冗余后的 Markdown 更方便。

根项目已经安装 `pandoc-wasm`，希望通过 Pandoc 转换，在 HTML、EPUB 之外增加 Markdown 输出格式；同时把项目后端整体迁移为原生 ESM，以兼容 WASM 和未来仅提供 ESM 的 npm 包。

## 已确认的 Markdown 行为

1. 使用 `pandoc-wasm@1.1.0` 内置的 Pandoc 3.10，将 HTML 转换为 UTF-8 GitHub Flavored Markdown。
2. 转换使用与 `gfm-raw_html`、`wrap: none` 等价的语义：移除 CSS、布局容器、HTML 版侧栏和无意义原始 HTML，保留标题层级、正文、作者等可见元数据、来源链接、列表、引用、代码、表格和必要图片信息。
3. 图片质量为“无图”时删除图片；其他模式保留图片替代文本和原始远程地址，不复制本地图片，生成适合单文件提交给 AI 的轻量文本。
4. 单个文件的 Pandoc 转换失败时，把原始 HTML 作为合法 Markdown 写入带失败标记的 `.md` 文件；回退写入成功即视为可用产物，不把整本书标记为 `partial_success`，但必须记录结构化 WARN、失败原因和 `fallbackCount`。
5. 回退文件名统一采用 `<原名>.pandoc-failed.md`。如果输出包含多文件，内部链接必须改写到实际生成的 `.md` 或 `.pandoc-failed.md`，不得保留失效的 `.html` 链接。
6. 如果连回退文件也无法写入，才属于真实输出失败：其他格式已经成功时为 `partial_success`，没有任何可用产物时为 `failure`。现有缺图导致的 `partial_success` 语义保持不变。
7. 最近五日输出历史增加 Markdown 入口，并与 HTML、EPUB 使用同一安全路径、日志和打开失败提示。
8. 每次任务强制生成 HTML、Markdown、EPUB 三种格式，GUI 不再提供输出格式选择。读取旧配置中的 HTML-only/EPUB-only 子集时归一化为三种格式，保存配置时固定写出三项。
9. 每本书镜像转换全部 HTML：信息页、内容页、目录页和单文件版都转换。输出为 `markdown/<安全书名>/html/<同名>.md` 与 `markdown/<安全书名>/单文件版/<安全书名>.md`，不复制 CSS 和图片；最近输出历史打开书级 Markdown 目录。

## 已确认的 ESM 迁移边界

“项目整体迁移 ESM”按 Electron 的运行时边界解释为应用模块图使用原生 ESM，而不是强制仓库内每一个 JavaScript 文件都使用 ESM：

1. 根 `package.json` 增加 `"type": "module"`；Electron 主进程、CLI、后端业务模块和 Markdown Worker 输出为原生 ESM，产物仍位于 `dist/**/*.js`。
2. Babel 继续负责 TS/TSX、装饰器和静态资源复制，但不再把模块转换为 CommonJS；TypeScript 切换到 NodeNext/ESM 校验，内部导入必须生成 Node.js ESM 可解析的显式路径。
3. 两个 Electron preload 运行在默认 sandbox 下。根据 Electron 的 ESM 限制，它们保留为明确的 `.cjs` 边界；不得为了追求“纯 ESM”而关闭 sandbox。需要加载 ESM 产物的维护脚本改用动态 `import()`，其他 `.cjs` 工具脚本可以保留。
4. Vite 前端原本就是 ESM 源码和浏览器 bundle；传统浏览器脚本不属于 Node.js 模块迁移范围。
5. `pnpm start` 继续只启动已有的 `dist/index.js`，不触发构建；开发期间仍由 `pnpm watch` 独立更新 `dist`，`pnpm startgui` 的前端调试语义不变。
6. `__dirname`、`~/src/*` 别名、无扩展名和目录导入、CJS 测试运行器以及直接 `require(dist)` 的脚本都必须完成迁移，并分别验证主进程、CLI、在线 runner、文档截图脚本、SQLite、Sharp 和 Electron 打包产物。
7. Pandoc 仅在独立 Worker 中加载并串行转换，避免同步 WASM 调用阻塞 Electron 主线程。WASM 不从网络加载，安装包必须携带可读取的 `pandoc.wasm`。

Electron 官方边界参考：[ES Modules in Electron](https://www.electronjs.org/docs/latest/tutorial/esm)。

## 已确认的发行许可

1. ZhihuHelp 自有代码采用 `MIT OR GPL-2.0-or-later` 双重许可；第三方代码仍遵循各自许可证，不宣称为 MIT。
2. 含 Pandoc 的桌面安装包整体按 `GPL-2.0-or-later` 发布，并附 GPL 文本、第三方声明和源码/构建获取说明。
3. 每个二进制 Release 同时提供该版本的完整对应源码和构建脚本，包括精确版本的 ZhihuHelp、`pandoc-wasm` 与 Pandoc 源码或合规的源码提供方式。
4. 当前 Git 仓库实际只跟踪根 `LICENSE`；`node_modules` 被忽略，npm 安装得到的 `pandoc-wasm` 包含转换包装代码和 `pandoc.wasm`，但不包含 Pandoc 3.10 的完整对应源码及全部构建脚本。因此本期必须补齐双许可证、第三方声明和 Release 对应源码产物，不能把本地 `node_modules` 视为已经完成源码提供。

以上为工程合规边界，不是法律意见。GPLv2 第 3 节参考：[GNU GPL 2.0](https://www.gnu.org/licenses/old-licenses/gpl-2.0.html)。

## 实施结果与验收

1. Electron 主进程、CLI、后端与 Markdown Worker 已输出为原生 ESM；两个 sandbox preload 明确保留为 `.cjs`。`pnpm start` 仍只启动现有 `dist/index.js`，构建继续由 `pnpm watch` 或显式 build 命令负责。
2. 任务配置与 GUI 已取消格式选择，并在读取旧子集配置时归一化为固定的 HTML、Markdown、EPUB 三项。生成链路会把每本书的信息页、内容页、目录页和单文件版全部镜像转换为 Markdown。
3. Pandoc 在按需创建的独立 Worker 中串行运行并跨分卷复用；文件级转换失败会生成 `.pandoc-failed.md`，只有 Markdown 最终写入或发布失败才使该书进入 `partial_success`。结构化日志、诊断导出和最近五日输出历史均已接入 Markdown 路径与回退计数。
4. 发布材料已包含 MIT/GPL 双许可证、第三方声明和对应源码说明；Windows/macOS Release 工作流会先生成并上传固定版本、固定哈希的对应源码包，再上传二进制产物。发布目录会校验 Pandoc WASM 与许可文件。
5. 离线测试通过，共 44 个测试文件、211 项测试；TypeScript、ESLint、后端构建、前端构建、VitePress 构建与 15 条公开路由校验均通过。在线签名冒烟通过 8 个公开样本。
6. `pnpm pack`、unpacked 许可/WASM/Sharp/SQLite 校验及 `pnpm dist` 均通过，已生成 Windows NSIS 安装包和 blockmap。`pnpm startgui` + `pnpm start`、unpacked 应用各持续运行 15 秒且未退出，冒烟创建的进程树和 8080 端口均已清理。
